TỔNG QUAN

Snort là gì và chạy như thế nào

Snort là hệ thống phát hiện và ngăn chặn xâm nhập mạng mã nguồn mở, hoạt động dựa trên rule. Hình dung nó như bảo vệ ở cổng tòa nhà: có thể chỉ đứng nhìn, có thể ghi sổ ra vào, hoặc cầm sổ ảnh kẻ gian để báo động và chặn cổng.

Đường đi của một gói tin bên trong Snort

  1. Packet DecoderThu gói tin từ card mạng hoặc file và bóc tách các lớp.
  2. Pre-processorsSơ chế: ghép mảnh, giải mã, chuẩn hóa để khó bị lách.
  3. Detection EngineSo gói tin với từng rule. Đây là bộ phận chính.
  4. Logging & AlertingGhi log và tạo cảnh báo khi có rule khớp.
  5. Outputs & PluginsĐưa kết quả ra file, syslog, cơ sở dữ liệu.

CHẾ ĐỘ 1

Sniffer: xem gói tin trực tiếp

Snort đọc gói tin đi qua card mạng và in ngay lên màn hình, giống tcpdump. Không cần file cấu hình. Nhấn Ctrl + C để dừng, Snort sẽ in bảng thống kê số gói đã bắt.

Dùng khiKiểm tra nhanh mạng có lưu lượng không, máy nào đang nói chuyện với máy nào, hoặc xem nội dung một giao thức không mã hóa.
Không hợp khiLưu lượng lớn hoặc cần xem lại sau. Màn hình trôi rất nhanh và không lưu gì.
Tham sốIn thêm cái gìVí dụ dễ nhớ
-vPhần đầu gói tin: IP, cổng, TTL, cờ TCPĐịa chỉ trên phong bì
-dNội dung bên trong (payload)Lá thư trong phong bì
-eTầng liên kết: địa chỉ MACBiển số xe đưa thư
-XToàn bộ gói tin dạng HEX, kể cả các headerPhim chụp X-quang cả bức thư
Các cách gọi thường dùng
sudo snort -v              # chỉ header
sudo snort -vd             # header + nội dung
sudo snort -de             # nội dung + MAC
sudo snort -v -d -e        # cả ba, viết gộp -vde cũng được
sudo snort -X              # mọi thứ ở dạng HEX
sudo snort -v -i eth0      # chỉ định card mạng
sudo snort -eX             # MAC + toàn bộ gói dạng HEX
sudo snort -v -n 10        # bắt 10 gói rồi dừng

CHẾ ĐỘ 2

Packet Logger: lưu gói tin vào file

Thêm -l là Snort chuyển sang ghi gói tin ra đĩa. Các chữ v, d, e quyết định ghi chi tiết đến đâu, còn -l quyết định cất vào thư mục nào.

Dùng khiCần bằng chứng để điều tra, cần mở lại bằng Wireshark hay tcpdump, hoặc muốn có dữ liệu để thử rule.
Lưu ý quyềnFile log thuộc root. Muốn mở phải dùng sudo, hoặc đổi chủ: sudo chown ubuntu file.
Tham sốÝ nghĩa
-l .Lưu log vào thư mục hiện tại. Bỏ trống thì mặc định là /var/log/snort.
-K ASCIILưu dạng văn bản đọc được, chia thư mục theo địa chỉ IP.
-r <file>Đọc lại file log (dạng nhị phân) bằng Snort.
-n 10Chỉ đọc 10 gói đầu.
Ghi log
sudo snort -dev -l .               # nhị phân, tạo file snort.log.<dãy số>
sudo snort -dev -K ASCII -l .      # văn bản, mỗi IP một thư mục

Đọc lại file log

Đọc và lọc
sudo snort -r snort.log.1638459842              # đọc toàn bộ
sudo snort -r snort.log.1638459842 -X -n 10     # 10 gói đầu, dạng HEX

CHẾ ĐỘ 3

IDS/IPS: cảnh báo và chặn theo rule

Đây là chế độ chính. Snort so từng gói tin với bộ rule: khớp thì cảnh báo (IDS) hoặc chặn (IPS). Chế độ này bắt buộc phải có -c trỏ tới file cấu hình hoặc file rule.

Dùng IDS khiMuốn giám sát mà không rủi ro làm gián đoạn mạng, hoặc đang thử rule mới.
Dùng IPS khiRule đã đủ tin cậy và bạn muốn chặn tự động. Chặn nhầm sẽ làm gián đoạn người dùng thật.
Tham sốÝ nghĩa
-c <file>Nạp file cấu hình (snort.conf) hoặc file rule.
-TKiểm tra cấu hình có lỗi không rồi thoát.
-NTắt ghi log. Màn hình vẫn hiện nếu có -v hoặc -X.
-DChạy ngầm (daemon), không hiện gì trên màn hình.
-A <kiểu>Chọn kiểu cảnh báo, xem bảng dưới.
-l <thư mục>Nơi đặt file alert và file log. Mặc định /var/log/snort.

Năm kiểu cảnh báo của -A

KiểuHiện trên màn hìnhGhi file alertNội dung
consoleCóKhôngMỗi cảnh báo một dòng: thời gian, tên rule, IP hai bên
cmgCóKhôngNhư console, kèm header và nội dung HEX của gói tin
fastKhôngCóTóm tắt một dòng cho mỗi cảnh báo
fullKhôngCóĐầy đủ mọi thông tin. Đây là kiểu mặc định
noneKhôngKhôngKhông cảnh báo, vẫn ghi log nhị phân

Ở mọi kiểu, các gói tin làm rule kêu vẫn được ghi vào file snort.log.*, trừ khi bạn thêm -N. File alert được ghi nối tiếp qua các lần chạy, nên hãy xóa file cũ trước khi đếm cảnh báo.

Chạy IDS
sudo snort -c /etc/snort/snort.conf -T                 # kiểm tra cấu hình
sudo snort -c /etc/snort/snort.conf -A console         # cảnh báo ra màn hình
sudo snort -c /etc/snort/snort.conf -A full -l .       # ghi file alert tại thư mục này
sudo snort -c /etc/snort/snort.conf -A console -N      # không ghi log
sudo snort -c /etc/snort/rules/local.rules -A console  # chỉ dùng file rule, để thử rule

  • GID: bộ phận sinh cảnh báo (1 = rule thường)
  • SID: mã số rule, dùng để tra ngược rule nào đã kêu
  • REV: số lần rule được sửa

Chạy ngầm

Chuyển sang IPS

Chế độ chặn
sudo snort -c /etc/snort/snort.conf -q -Q --daq afpacket -i eth0:eth1 -A console
Tham sốÝ nghĩa
-QBật chế độ inline, tức Snort được quyền chặn.

CHẾ ĐỘ 4

PCAP: điều tra file lưu lượng có sẵn

Thay vì nghe từ card mạng, Snort đọc một file PCAP và xử lý như thể lưu lượng đang chạy thật. Kết hợp được với mọi tham số ở ba chế độ trên.

Dùng khiĐiều tra sau sự cố, kiểm tra một file nghi vấn, hoặc thử rule mới trên dữ liệu đã biết kết quả.
Nhận được gìNội dung gói tin, cảnh báo theo rule, và bảng thống kê: số gói theo giao thức, số phiên TCP, số HTTP GET/POST, số cảnh báo.
Tham sốÝ nghĩa
-r file.pcapĐọc một file. Viết dài là --pcap-single=.
--pcap-list="a.pcap b.pcap"Đọc nhiều file, cách nhau bằng dấu cách.
--pcap-dir=/home/pcap-folderĐọc mọi file PCAP trong một thư mục.
--pcap-showIn tên file đang xử lý, để biết cảnh báo thuộc file nào.
Phân tích PCAP
sudo snort -r icmp-test.pcap                                        # chỉ xem thống kê
sudo snort -c /etc/snort/snort.conf -q -r icmp-test.pcap -A console -n 10
sudo snort -c /etc/snort/snort.conf -A full -l . -r mx-1.pcap       # ghi alert và log
sudo snort -c /etc/snort/snort.conf -q --pcap-list="mx-2.pcap mx-3.pcap" -A console --pcap-show
sudo snort -c /etc/snort/snort.conf -q --pcap-dir=/home/pcap-folder -A console    # cả một thư mục

Các con số như "HTTP GET methods" hay "TCP Segments Queued" nằm trong bảng thống kê in ra cuối cùng. Bảng này dài, có thể lưu ra file để lọc: thêm 2>&1 | tee ketqua.txt vào cuối lệnh, rồi grep -i "GET methods" ketqua.txt.

VIẾT RULE · PHẦN 1

Cấu trúc một rule

Rule là một dòng mô tả "gặp gói tin như thế này thì làm gì". Nó gồm hai phần: header bắt buộc, nói về ai gửi cho ai, và options trong ngoặc đơn, mô tả chi tiết hơn. Rule tự viết đặt trong /etc/snort/rules/local.rules.

Hành động (action)

Từ khóaLàm gìDùng ở
alertTạo cảnh báo và ghi log gói tinIDS, IPS
logChỉ ghi log gói tin, không cảnh báoIDS, IPS
dropChặn gói tin và ghi logIPS
rejectChặn, ghi log và chủ động ngắt phiên kết nốiIPS
passBỏ qua gói tin, dùng để loại trừ lưu lượng tin cậyIDS, IPS

Giao thức (protocol)

Snort 2 chỉ nhận bốn giá trị ở vị trí này: ip, tcp, udp, icmp. Muốn bắt giao thức tầng ứng dụng như FTP hay HTTP thì dùng tcp kèm số cổng (21, 80) và options.

Rule options

Options nằm trong ngoặc đơn, mỗi mục có dạng tên:giá trị;. Chúng chia thành bốn nhóm.

Nhóm soi nội dung (payload)

OptionTác dụngVí dụ
contentTìm một chuỗi trong nội dung gói tin. Viết dạng chữ, dạng HEX giữa hai dấu |, hoặc trộn cả hai. Dùng được nhiều lần trong một rule.content:"GET";

VIẾT RULE · PHẦN 2B

Soi nội dung chính xác: vị trí, ký tự đặc biệt, pcre

Mặc định content tìm ở bất kỳ đâu trong payload. Các option dưới đây giới hạn vị trí tìm, giúp rule ít báo nhầm và chạy nhanh hơn. Chúng phải đứng ngay sau content mà chúng bổ nghĩa.

WRITING RULES · PART 2B

Precise payload matching: position, special characters, pcre

By default content searches anywhere in the payload. The options below limit where it searches, so the rule raises fewer false alerts and runs faster. They must come right after the content they modify.

Limiting the position

OptionEffectExample
offset:nStart searching at byte n of the payload (counting from 0).content:"SMB"; offset:5;
depth:nSearch only the first n bytes (counted from offset if set).content:"530 "; depth:4;
distance:nThis content must start at least n bytes after the previous content.content:"USER "; content:"admin"; distance:0;
within:nThis content must fit entirely within the n bytes after the previous content.content:"GET "; content:".php"; within:100;
Why depth matters
# Without depth: also matches "226 Transfer complete. 530 bytes sent"
alert tcp any 21 -> any any (msg:"FTP login fail"; content:"530 "; sid:1000101; rev:1;)
# With depth:4: matches only when "530 " starts the reply
alert tcp any 21 -> any any (msg:"FTP login fail"; content:"530 "; depth:4; sid:1000101; rev:2;)

Text or HEX

Both give Snort the same bytes. Use text when you can type it; put HEX between two | signs when you cannot. You can mix both in one string: content:"|89|PNG|0D 0A 1A 0A|";.

Upper and lower case are different bytes. Lower case = upper case + 0x20: GET is 47 45 54, get is 67 65 74. Add nocase to match both; nocase also applies to HEX bytes that are letters.

content looks for a fixed string; pcre uses a regular expression, so one rule catches a whole family of strings. Syntax: pcre:"/pattern/flags";.

pcre examples
# Executable downloaded over FTP: content filters fast, pcre checks after

# Failed login with any user name
alert tcp any 21 -> any any (msg:"FTP login fail"; content:"530 "; depth:4; pcre:"/^530 User \w+ cannot log in/"; sid:1000103; rev:1;)
# Test the pattern in the terminal before putting it in a rule
echo "RETR setup.exe" | grep -P '^RETR\s+\S+\.(exe|dll|bat|ps1)'

pcre trap. The |57 69| syntax belongs to content only; inside pcre | means "or", so /|57 69|/ contains an empty alternative and matches almost every packet. Write HEX in pcre as \x57\x69. Avoid ; and " in the pattern (use \x3B, \x22). Always pair pcre with a content, because pcre is much slower.

VIẾT RULE · PHẦN 3

Ví dụ rule theo mục đích

Mỗi ví dụ dùng một SID riêng từ 1.000.001 trở đi. Khi chép vào local.rules, mỗi rule nằm trên một dòng.

Phát hiện ping

Báo mọi gói ICMP, cả lượt hỏi lẫn lượt đáp. Dùng để kiểm tra Snort có hoạt động không. Ngoài thực tế rule này gây ngập cảnh báo.

alert icmp any any <> any any (msg:"ICMP Packet Found"; sid:1000001; rev:1;)

Theo dõi một máy hoặc một mạng con

Chỉ báo ICMP xuất phát từ máy đang bị nghi ngờ, hoặc từ mọi máy ngoài mạng nội bộ.

alert icmp 192.168.1.56 any -> any any (msg:"ICMP From Suspect Host"; sid:1000002; rev:1;)
alert icmp !192.168.1.0/24 any -> 192.168.1.0/24 any (msg:"ICMP From Outside"; sid:1000003; rev:1;)

Giám sát một dịch vụ theo cổng

Báo hoạt động trên cổng FTP (21) và Telnet (23), hai dịch vụ truyền mật khẩu không mã hóa.

alert tcp any any <> any 21 (msg:"FTP Port 21 Activity"; sid:1000004; rev:1;)
alert tcp any any <> any [21,23] (msg:"FTP or Telnet Activity"; sid:1000005; rev:1;)

Bắt lưu lượng tới cổng hệ thống

Báo kết nối TCP tới các cổng từ 1 đến 1024, nơi đặt phần lớn dịch vụ quan trọng.

alert tcp any any -> any 1:1024 (msg:"TCP System Port Activity"; sid:1000006; rev:1;)

Tìm chuỗi trong nội dung

Báo yêu cầu HTTP GET. Bản thứ hai viết cùng chuỗi ở dạng HEX và không phân biệt hoa thường.

alert tcp any any -> any 80 (msg:"GET Request Found"; content:"GET"; sid:1000007; rev:1;)
alert tcp any any -> any 80 (msg:"GET Request Found"; content:"|47 45 54|"; nocase; sid:1000008; rev:1;)

Phát hiện dò quét bằng cờ TCP

Gói chỉ có cờ SYN là bước mở đầu kết nối. Rất nhiều gói SYN tới nhiều cổng là dấu hiệu quét cổng. Rule thứ hai bắt gói mang dữ liệu (PSH + ACK).

alert tcp any any -> any any (msg:"SYN Packet"; flags:S; sid:1000009; rev:1;)
alert tcp any any -> any any (msg:"PSH-ACK Packet"; flags:PA; sid:1000010; rev:1;)

Lọc theo IP ID hoặc kích thước

Truy đúng một gói tin khi đã biết IP ID, hoặc bắt các gói có nội dung nằm trong một khoảng kích thước.

alert tcp any any <> any any (msg:"IP ID 35369"; id:35369; sid:1000011; rev:1;)
alert ip any any <> any any (msg:"Payload 100-300 byte"; dsize:100<>300; sid:1000012; rev:1;)

Gói tin có IP nguồn trùng IP đích

Lưu lượng bình thường không bao giờ như vậy. Đây là dấu hiệu gói tin bị giả mạo.

alert ip any any <> any any (msg:"Same IP Source and Destination"; sameip; sid:1000013; rev:1;)

Chặn ở chế độ IPS

Cùng cấu trúc, chỉ đổi hành động. drop lặng lẽ bỏ gói, reject bỏ gói và báo cho bên gửi là kết nối bị từ chối.

drop icmp any any -> 192.168.1.0/24 any (msg:"Block Inbound Ping"; sid:1000014; rev:1;)
reject tcp any any -> any 23 (msg:"Reject Telnet"; sid:1000015; rev:1;)

Chỉ ghi lại, không cảnh báo

Lưu toàn bộ lưu lượng DNS để phân tích sau mà không làm đầy file cảnh báo.

log udp any any -> any 53 (msg:"DNS Query"; sid:1000016; rev:1;)

Quy trình viết và thử một rule

  1. Mở file rule: sudo gedit /etc/snort/rules/local.rules (hoặc sudo nano).
  2. Thêm rule mới trên một dòng. Rule cũ không dùng nữa thì thêm # ở đầu dòng để tắt.
  3. Xóa file cảnh báo cũ để khỏi đếm nhầm: sudo rm alert.
  4. Chạy thử trên một file PCAP: sudo snort -c /etc/snort/rules/local.rules -A full -l . -r task9.pcap
  5. Đọc kết quả: sudo cat alert, hoặc xem số cảnh báo trong bảng thống kê cuối màn hình. File alert không chứa nội dung gói; muốn xem payload thì đọc file log bằng sudo snort -r snort.log.<số> -d (xem mục Điều tra kết quả).

Lỗi hay gặp. Thiếu dấu ; cuối một option, thiếu ngoặc đóng, trùng SID với rule khác, hoặc dùng dấu nháy cong thay cho ". Snort sẽ báo số dòng bị lỗi khi khởi động.

INVESTIGATING RESULTS

Reading, filtering and counting results

Writing the rule is half the job. The other half is pulling the right information out of what Snort prints or saves.

Pick a workflow

What you needCommand
Alerts with payload on screen, no files createdsudo snort -c local.rules -r file.pcap -A cmg -N -q
Only a count or a list of alertssudo snort -c local.rules -r file.pcap -A console -N -q
Save for later, then read the payloadsudo snort -c local.rules -r file.pcap -A full -l .
sudo snort -r snort.log.<number> -d

The alert file has no payload. It records the rule name, IPs, ports and header fields. Packet content lives in snort.log.* and only shows when read with -d.

Filter and count

Filtering recipes
# Drop the "WARNING: No preprocessors..." lines (they go to stderr)
sudo snort -c local.rules -r file.pcap -A console -N -q 2>/dev/null

# Total alerts (-q hides the "Alerts:" line at the end)
... 2>/dev/null | grep -c "\[\*\*\]"

# Hits per rule, most frequent first
... 2>/dev/null | grep -o '\[1:[0-9]*:[0-9]*\] [^[]*' | sort | uniq -c | sort -rn

# One rule only, by SID
... 2>/dev/null | grep -c "1:1000002:"

# Frequency per minute (cut -c1-14 for per second)
... 2>/dev/null | cut -c1-11 | sort | uniq -c

# Find a string in the payload, with a few lines around it
sudo snort ... -A cmg -N -q 2>/dev/null | grep -i -B 8 -A 2 "IPC"

... stands for the start of the -A console command above. Without -q, the end of the output has an Action Stats block whose Alerts: line is the total.

PROTOCOL REFERENCE

  
Protocol and file signatures

  
These signs belong to the traffic itself, not to any tool. Snort, Suricata, Wireshark and tcpdump only differ in how you search. A failed FTP login, for example: Snort content:"530 "; depth:4;, Wireshark ftp.response.code == 530.

  
FTP (port 21)

  
Login sequence: 220 banner → client USER → 331 → client PASS → 230 success or 530 failure. FTP is unencrypted, so user names and passwords are readable in the pcap. File content travels over a separate data connection, not port 21.

MIME type

  
A label declaring the kind of data, written type/subtype. Content-Type: is the sender saying "this is what I send"; Accept: is the requester saying "this is what I want". BitTorrent

  
A .torrent file (metafile) holds no data, only instructions: the tracker address (announce), name, size, piece size and a hash per piece. It is bencoded and usually starts with d8:announce. When the client asks the tracker, the packet looks like GET /announce?info_hash=...&peer_id=..., with Accept: application/x-bittorrent, the tracker in Host: and the client name in User-Agent:.
