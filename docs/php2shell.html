1Overview: what actually happens?

PHP is a server-side language behind most of the world's websites. "PHP2Shell" is the name of a chain of flaws living inside PHP itself (the core runtime), not in the website or framework on top of it.

The scary part: the attacker needs no login and no special feature on the site. Just a few ordinary HTTP requests to any PHP page that accepts POST — even a page that prints only the word OK — is enough to run commands on the server.

Two flaws combine into one complete attack:

CVERoleResult
CVE-2026-109618Memory leakReads secret addresses → defeats the ASLR defense
CVE-2026-109619Hijacks executionRuns arbitrary commands (RCE) as the web-server user

The bug has existed since PHP 5.4.0 (2012) — roughly 14 years of releases at once. Patched in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35.

Core message to teach: "Not logged in" does NOT mean "safe". Some PHP mechanisms run and write data before your application's first line of code.

2Glossary for beginners

Read this first and the later sections become much easier.

Request / POST
Each time the browser talks to the server is a "request". GET = "show me", POST = "I'm submitting data" (posting, uploading a file). The submitted data is the request body.
Session & PHPSESSID
A session is the "private notebook" the server keeps for each user. The server recognizes you by a random code sent in a cookie named PHPSESSID.
session.upload_progress
A PHP feature that reports "the upload is X% done". While receiving a file, PHP writes progress into the session. Enabled by default.
Pointer & Dangling pointer
A pointer is a "slip of paper holding the address" of some memory. If that memory is freed (returned) but the slip still points at it, you have a dangling pointer — pointing at a place no longer valid.
Use-after-free
The "using freed memory again" bug. If an attacker slips forged data into the exact memory just released, the program misreads it and acts on the fake data.
ASLR
Address Space Layout Randomization — randomly shuffles where memory regions sit on each run, so the attacker can't guess the address to aim at.
Memory leak
Here it means being able to read out the process's memory, revealing the real addresses — the step needed to beat ASLR.
RCE
Remote Code Execution — running arbitrary commands/code on the server from afar. The highest severity level.
www-data
The system account the web server (Apache/Nginx) runs as on Linux. The attacker's commands run with exactly this user's privileges.
Container / Docker
A "box" that packages an app plus its environment, running the same on any machine. In the lab the target server is built with Docker for safe practice.

4Step-by-step explanation

Step 1 — A harmless feature: Upload Progress

When you upload a large file, PHP receives the data while writing progress (file name, size, bytes received) into $_SESSION, so another page can read it and report the percentage. This feature is on by default and is triggered when a form contains a field named PHP_SESSION_UPLOAD_PROGRESS.

The key detail: this writing happens while PHP is reading the submitted data, i.e. before the page's code runs. The unintended consequence: an attacker can affect the server's memory without logging in, and any page that accepts POST is affected.

Analogy: Your code is the guard checking IDs at the door. But upload_progress is like a clerk standing in front of the door: the moment someone hands over a package, the clerk records their details — before the guard can ask for ID.

Step 2 — The bug: a bailout at the wrong moment

On an out-of-memory condition, PHP performs a "bailout" (emergency exit) to abort the request. In a special case, the cleanup step — clearing the pointer after freeing the memory — is skipped. Result: the memory is freed but the pointer still points at it → a dangling pointer.

Analogy: You check out of a hotel but never tear up the card that says "my room is 305". The next request on the same worker follows that old card into a room someone else (other data) now occupies.

This is exactly CWE-824: the next request on the same worker follows a pointer that was never reset.

Step 3 — Recon: confirming the target

Before attacking, confirm the target really is a vulnerable PHP. In the lab this is confirmed by standing up a PHP container and checking its version:

# Confirm the container is running and the PHP version
docker ps
docker exec php2shell-target php -v   # → PHP 8.4.26

# The target page only prints "OK" — no special feature
curl -s http://127.0.0.1:8088/index.php   # OK

Meaning: it proves the flaw is not in the application. Even the most harmless page is attackable, because the bug lives in PHP's core.

Step 4 — Leak memory, defeat ASLR CVE-2026-109618

ASLR stops the attacker from knowing where things sit in memory. This step reads out memory to reveal real addresses, thereby defeating ASLR. The leaked data is returned to the attacker through the Set-Cookie response header (normally used to issue PHPSESSID).

The leak is run twice:

  • Pass 1: reveals the base address of the heap (dynamic memory).
  • Pass 2: reveals the base address of the PHP library (libphp) — where system() lives.
Analogy: Every morning the shop rearranges all its shelves (ASLR). A thief must first walk around to learn "which shelf is where today" (the leak) before acting. The two leak passes are those two scouting rounds.

Step 5 — From a leak to a shell CVE-2026-109619

Knowing the real addresses, the attacker re-occupies the freed memory with a forged internal structure whose cleanup pointer (destructor) points to the address of system(). When the engine "cleans up" that value at the end of request handling, it believes it is calling a harmless destructor but actually calls system() with an attacker-controlled string — a command that runs on the server.

The command runs as www-data (the web-server user). Proof in the lab: running id returns uid=33(www-data).

This document explains at a conceptual level for defense and teaching — it does not present detailed exploit code.

5How to detect it (defense)

Signs in logs & traffic

  • Unusual upload_progress fields: many POST requests carrying a PHP_SESSION_UPLOAD_PROGRESS field sent to endpoints with no upload feature at all — highly suspicious.
  • Odd Set-Cookie headers: abnormally long PHPSESSID values or ones containing strange/binary bytes — possibly memory leaking out.
  • Workers crashing and restarting repeatedly: many out-of-memory (OOM) errors or PHP segfaults in a short window — a sign memory is being hammered.
  • Fast, repeated POST bursts to the same harmless page, with the cookie changing each time.
  • Strange commands running as www-data: e.g. id, reading sensitive files, child processes spawned from Apache/PHP-FPM.

Helpful tools

  • IDS/IPS (Snort, Suricata): write a rule detecting a request body containing PHP_SESSION_UPLOAD_PROGRESS to unexpected endpoints, or oversized Set-Cookie responses.
  • WAF (ModSecurity): block/log suspicious POST patterns.
  • Version monitoring: inventory all servers for unpatched PHP (the most reliable detection).
  • EDR / process auditing: alert when the web server spawns an unexpected shell.

6How to fix it

Priority #1 — Patch PHP

Upgrade to a patched build: PHP 8.5.12, 8.4.27, 8.3.36 or 8.2.35 (or newer). This is the definitive fix; everything below is defense-in-depth.

Reduce the attack surface (if you can't patch immediately)

; in php.ini — turn the feature off if unused
session.upload_progress.enabled = Off

; tighten session handling
session.use_strict_mode = On
  • Disable session.upload_progress when the app doesn't use an upload progress bar — closes the trigger path immediately.
  • Enable session.use_strict_mode so PHP won't accept session IDs the client invents.
  • Run PHP with least privilege: limit what www-data can do (minimal write access, minimal system commands).
  • Defense in depth: WAF, IDS, process monitoring — to block or spot it early even if one layer is bypassed.
  • Isolate with containers & seccomp/AppArmor: limit damage if the server is compromised.
General principle: turn off default features you don't use, run services with least privilege, and keep patches current — these three habits block a whole class of flaws, not just PHP2Shell.

7Outline for teaching others

A suggested speaking order, with a few opening lines to lead with.

① Open with the paradox

"A web page that prints only the word OK, with no login box and no upload feature. And yet an attacker runs commands on the server. How?"

② Point to the root: the bug is below the application

"Because the flaw isn't in the website — it's in PHP's core, the layer beneath every framework. So even perfectly clean code is affected."

③ Tell the 5-link chain — use the diagram in Section 3. One line each: harmless feature → the bug → recon → leak defeats ASLR → get a shell.

④ Use the analogies (the clerk standing in front of the door; rearranging shelves every morning) so non-specialists follow.

⑤ Close with defense — the part that matters most to the audience:

"Three things to do: patch PHP; disable upload_progress if unused; and monitor for anomalies like oversized Set-Cookie headers or workers crashing repeatedly."

⑥ A memorable closing line

"'Not logged in' doesn't mean 'safe'. Some mechanisms run before your very first line of code."

1Tổng quan: chuyện gì xảy ra?

PHP là ngôn ngữ chạy phía máy chủ, đứng sau phần lớn website trên thế giới. "PHP2Shell" là tên một chuỗi lỗ hổng nằm ngay trong bản thân PHP (phần lõi runtime), không phải lỗi của website hay framework bên trên.

Điểm đáng sợ: kẻ tấn công không cần đăng nhập, không cần website có chức năng gì đặc biệt. Chỉ cần gửi vài yêu cầu HTTP bình thường tới bất kỳ trang PHP nào nhận POST — kể cả một trang chỉ in đúng chữ OK — là có thể chạy được lệnh trên máy chủ.

Hai lỗ hổng ghép lại thành một đòn hoàn chỉnh:

CVEVai tròKết quả
CVE-2026-109618Rò rỉ bộ nhớ (memory leak)Đọc trộm địa chỉ bí mật → phá lớp bảo vệ ASLR

Lỗi tồn tại từ PHP 5.4.0 (2012), tức ảnh hưởng ~14 năm phiên bản cùng lúc. Được vá trong PHP 8.5.12, 8.4.27, 8.3.36 và 8.2.35.

Thông điệp cốt lõi để giảng: "Chưa qua đăng nhập" KHÔNG đồng nghĩa với "an toàn". Một số cơ chế của PHP chạy và ghi dữ liệu trước cả dòng code đầu tiên của ứng dụng.

2Từ điển thuật ngữ cho người mới

Đọc phần này trước, các mục sau sẽ dễ hiểu hơn nhiều.

Request / POST
Mỗi lần trình duyệt nói chuyện với máy chủ là một "yêu cầu" (request). GET = "cho tôi xem", POST = "tôi nộp dữ liệu cho anh" (đăng bài, upload file). Phần dữ liệu nộp lên gọi là request body.
Session & PHPSESSID
Session là "cuốn sổ riêng" máy chủ giữ cho từng người dùng. Máy chủ nhận ra bạn qua một mã ngẫu nhiên gửi trong cookie tên PHPSESSID.
session.upload_progress
Tính năng của PHP để báo "upload đã lên bao nhiêu %". Khi đang nhận file, PHP vừa nhận vừa ghi tiến độ vào session. Bật sẵn mặc định.
Con trỏ (pointer) & Dangling pointer
Con trỏ là "tờ giấy ghi địa chỉ" của một vùng nhớ. Khi vùng nhớ đó đã được trả lại (giải phóng) mà tờ giấy vẫn còn trỏ tới đó, ta có dangling pointer (con trỏ bỏ lửng) — trỏ vào chỗ không còn hợp lệ.
Use-after-free
Lỗi "dùng lại vùng nhớ đã giải phóng". Nếu kẻ tấn công kịp nhét dữ liệu giả vào đúng vùng nhớ vừa được thả ra, chương trình sẽ hiểu nhầm và làm theo dữ liệu giả đó.
ASLR
Address Space Layout Randomization — cơ chế xáo trộn vị trí các vùng nhớ ngẫu nhiên mỗi lần chạy, để kẻ tấn công không đoán được địa chỉ cần nhắm tới.
Memory leak (rò rỉ bộ nhớ)
Ở đây nghĩa là đọc trộm được nội dung bộ nhớ của tiến trình, từ đó biết các địa chỉ thật — bước cần thiết để vượt qua ASLR.
RCE
Remote Code Execution — chạy được lệnh/mã tùy ý trên máy chủ từ xa. Đây là mức nghiêm trọng cao nhất.
www-data
Tài khoản hệ thống mà web server (Apache/Nginx) chạy dưới quyền đó trên Linux. Lệnh của kẻ tấn công chạy với đúng quyền này.
Container / Docker
"Chiếc hộp" đóng gói sẵn ứng dụng + môi trường, chạy độc lập và giống nhau trên mọi máy. Trong lab, máy chủ mục tiêu được dựng bằng Docker để thực hành an toàn.

4Giải thích từng bước

Bước 1 — Một tính năng vô hại: Upload Progress

Khi bạn upload file lớn, PHP vừa nhận dữ liệu vừa ghi tiến độ (tên file, dung lượng, số byte đã nhận) vào $_SESSION, để trang khác đọc và báo % cho trình duyệt. Tính năng này bật sẵn và được kích hoạt khi form có một trường tên PHP_SESSION_UPLOAD_PROGRESS.

Chi tiết then chốt: việc ghi này xảy ra ngay trong lúc PHP đọc dữ liệu gửi lên, tức trước cả khi code của trang chạy. Hệ quả ngoài ý muốn: kẻ tấn công tác động được vào bộ nhớ máy chủ mà không cần đăng nhập, và bất kỳ trang nào nhận POST cũng dính.

Ví dụ: Code của bạn là người bảo vệ kiểm tra giấy tờ ở cửa. Nhưng upload_progress như một nhân viên ghi sổ đứng trước cửa: ai đưa gói hàng là họ ghi thông tin vào sổ ngay, trước khi bảo vệ kịp hỏi giấy tờ.

Bước 2 — Cái bug: "bailout" sai thời điểm

Khi gặp tình huống hết bộ nhớ, PHP thực hiện một cú "bailout" (thoát khẩn cấp) để hủy yêu cầu. Trong tình huống đặc biệt, bước dọn dẹp — xóa con trỏ sau khi giải phóng vùng nhớ — bị bỏ qua. Kết quả: vùng nhớ đã được thả ra nhưng con trỏ vẫn trỏ tới đó → dangling pointer.

Ví dụ: Trả phòng khách sạn nhưng chưa xé tấm thẻ chỉ dẫn "phòng của tôi là 305". Yêu cầu kế tiếp trên cùng worker sẽ đi theo tấm thẻ cũ đó tới một căn phòng đã có người khác (dữ liệu khác) ở.

Đây đúng là tình huống CWE-824: yêu cầu kế tiếp trên cùng một worker đi theo một con trỏ chưa bao giờ được reset.

Bước 3 — Trinh sát: xác nhận mục tiêu

Trước khi đánh, kiểm tra mục tiêu đúng là PHP dính lỗi. Trong lab, điều này được xác nhận bằng cách dựng một container PHP và kiểm tra phiên bản:

# Xác nhận container đang chạy và đúng phiên bản PHP
docker ps
docker exec php2shell-target php -v   # → PHP 8.4.26

# Trang mục tiêu chỉ in "OK" — không có chức năng gì đặc biệt
curl -s http://127.0.0.1:8088/index.php   # OK

Ý nghĩa: chứng minh lỗ hổng không nằm ở ứng dụng. Trang vô hại nhất cũng tấn công được, vì lỗi nằm trong lõi PHP.

Bước 4 — Rò rỉ bộ nhớ, phá ASLR CVE-2026-109618

ASLR khiến kẻ tấn công không biết các thành phần nằm ở địa chỉ nào. Bước này đọc trộm bộ nhớ để lộ ra địa chỉ thật, qua đó vô hiệu hóa ASLR. Dữ liệu bị rò rỉ được máy chủ trả về cho kẻ tấn công thông qua header phản hồi Set-Cookie (vốn dùng để cấp PHPSESSID).

Đoạn rò rỉ được chạy hai lần:

  • Lần 1: lộ địa chỉ nền của vùng heap (bộ nhớ động).
  • Lần 2: lộ địa chỉ nền của thư viện PHP (libphp) — nơi chứa hàm system().
Ví dụ: Mỗi sáng cửa hàng đổi chỗ mọi kệ hàng (ASLR). Kẻ trộm phải đi một vòng dò xem "hôm nay kệ nào ở đâu" (leak) rồi mới ra tay. Hai lần leak chính là hai vòng dò đó.

Bước 5 — Từ leak đến shell CVE-2026-109619

Biết được địa chỉ thật rồi, kẻ tấn công chiếm lại vùng nhớ đã bị thả bằng một cấu trúc nội bộ giả, trong đó con trỏ dọn dẹp (destructor) được trỏ tới địa chỉ của system(). Khi engine "dọn dẹp" giá trị đó lúc kết thúc xử lý yêu cầu, nó tưởng đang gọi một hàm hủy vô hại nhưng thực ra gọi system() với chuỗi do kẻ tấn công kiểm soát — tức một lệnh chạy trên máy chủ.

Lệnh chạy dưới quyền www-data (user của web server). Bằng chứng trong lab: chạy id trả về uid=33(www-data).

Tài liệu này giải thích ở mức khái niệm để phục vụ phòng thủ và giảng dạy — không trình bày mã khai thác chi tiết.

5Cách nhận biết (phòng thủ)

Dấu hiệu trên log & mạng

  • Trường upload_progress bất thường: nhiều request POST chứa trường PHP_SESSION_UPLOAD_PROGRESS gửi tới các endpoint không hề có chức năng upload — rất đáng ngờ.
  • Header Set-Cookie khác thường: giá trị PHPSESSID dài bất thường hoặc chứa byte lạ/nhị phân — có thể là bộ nhớ bị rò rỉ ra ngoài.
  • Worker sập & khởi động lại liên tục: nhiều lỗi hết bộ nhớ (OOM) hoặc segfault của tiến trình PHP trong thời gian ngắn — dấu hiệu đang bị "dập" bộ nhớ.
  • Chuỗi request POST lặp nhanh tới cùng một trang vô hại, kèm cookie thay đổi mỗi lần.
  • Lệnh lạ chạy dưới quyền www-data: ví dụ id, cat file nhạy cảm, tiến trình con sinh ra từ Apache/PHP-FPM.

Công cụ hỗ trợ

  • IDS/IPS (Snort, Suricata): viết rule phát hiện request body chứa PHP_SESSION_UPLOAD_PROGRESS tới endpoint không mong đợi, hoặc Set-Cookie phản hồi quá khổ.
  • WAF (ModSecurity): chặn/log các mẫu POST đáng ngờ.
  • Giám sát phiên bản: rà soát toàn bộ máy chủ xem có bản PHP chưa vá không (đây là cách phát hiện chắc chắn nhất).
  • EDR / audit tiến trình: cảnh báo khi web server sinh tiến trình shell bất thường.

6Cách khắc phục

Ưu tiên số 1 — Vá PHP

Nâng cấp lên bản đã vá: PHP 8.5.12, 8.4.27, 8.3.36 hoặc 8.2.35 (hoặc mới hơn). Đây là biện pháp triệt để; mọi thứ bên dưới chỉ là lớp phòng thủ bổ sung.

Giảm bề mặt tấn công (nếu chưa vá được ngay)

; trong php.ini — tắt tính năng nếu không dùng
session.upload_progress.enabled = Off

; siết chặt cách xử lý session
session.use_strict_mode = On
  • Tắt session.upload_progress khi ứng dụng không dùng thanh tiến độ upload — đóng ngay con đường kích hoạt.
  • Bật session.use_strict_mode để PHP không chấp nhận session ID do client tự bịa.
  • Chạy PHP với quyền tối thiểu: giới hạn những gì www-data được phép làm (ít quyền ghi, ít lệnh hệ thống).
  • Phòng thủ nhiều lớp: WAF, IDS, giám sát tiến trình — để chặn hoặc phát hiện sớm ngay cả khi một lớp bị vượt.
  • Cô lập bằng container & seccomp/AppArmor: hạn chế thiệt hại nếu máy chủ bị chiếm.
Nguyên tắc chung rút ra: tắt tính năng mặc định không dùng đến, chạy dịch vụ với quyền tối thiểu, và luôn cập nhật bản vá — ba thói quen này chặn cả một lớp lỗ hổng chứ không riêng PHP2Shell.

7Dàn ý giảng cho mọi người

Gợi ý trình tự nói, kèm vài câu mở để bạn dẫn dắt.

① Mở đầu bằng nghịch lý

"Một trang web chỉ in đúng chữ OK, không có ô đăng nhập, không có chức năng upload. Vậy mà kẻ tấn công chạy được lệnh trên máy chủ. Tại sao?"

② Chỉ ra gốc rễ: lỗi nằm dưới ứng dụng

"Vì lỗi không nằm ở website, mà nằm trong chính lõi PHP — tầng bên dưới mọi framework. Nên dù bạn code sạch đến mấy vẫn dính."

③ Kể chuỗi 5 mắt xích — dùng đúng sơ đồ ở Mục 3. Mỗi mắt xích chỉ một câu: tính năng vô hại → cái bug → trinh sát → rò rỉ phá ASLR → chiếm shell.

④ Dùng phép ví von (người ghi sổ đứng trước cửa; đổi chỗ kệ hàng mỗi sáng) để lớp không chuyên vẫn nắm được.

⑤ Chốt bằng phòng thủ — phần quan trọng nhất với người nghe:

"Ba việc cần làm: cập nhật bản vá PHP; tắt tính năng upload_progress nếu không dùng; và giám sát các dấu hiệu bất thường như Set-Cookie quá khổ hay worker sập liên tục."
